# 待外部评审的长期问题清单

> 用途：请 Astra 针对下面每条给出技术意见。每条都写清"症状 / 证据 / 已试过什么 / 现在怎么兜 / 想请教的具体问题"，
> 不需要访问代码也能判断。相关仓库：设计系统 `<repo>`（`antopt`），守护 `<guard-repo>`（`aedt_guard`）。

## 0. 环境与前提

- Windows 单机；AEDT 2026 R1 + PyAEDT，通过 `ansysedt.exe -grpcsrv <port>` 由软件启动（可选 `-ng` 无界面）。
- 单实例 AEDT；一次真实求解 **20–25 分钟**（12 自适应次数更久）；一次优化迭代通常 2–4 个候选。
- 软件侧：本地 HTTP 服务 + 网页控制面，后台 worker 执行持久化队列（`queue.sqlite`），全部测试 **713 项**。
- 证据均在 `docs/evidence/*.json`、`docs/known_issues.md`、`docs/status.md`。

## 1. 扫频导出间歇性不完整（`E_SWEEP_EXPORT_INCOMPLETE`）

- **症状**：少数运行求解完成后导出 touchstone 只有 1 行或行数不足，带宽被算成 0；同一参数重跑常常正常。
  曾统计到约 30%（`docs/benchmarks.md`、早前 campaign 记录）。
- **已试**：guard 侧等待扫频完成再导出、按行数校验并重试；把扫频改为离散线性步长（24–30 GHz，步长 1.0）。
  部分缓解，未根除。
- **现有兜底**：导出不完整 → 该次运行判失败（不写假数据），允许重跑。
- **想请教**：
  1. AEDT/PyAEDT 里判断"sweep 已真正完成、可导出"的可靠信号是什么（`GetSetupStatus`？sweep 的 progress？还是必须等 `analyse` 返回）？
  2. 失败时能否只重导出而不重求解？我们尝试过 `get_solution_data` 重取，偶发仍少行。
  3. 这是否与 `-ng`、非交互会话或求解器并行设置有关？

## 2. 一次失败的报告创建会"毒化" PyAEDT worker 会话

- **症状**：`create_report(expressions=["dB(DirectivityTotal)"], report_category="Far Fields")` 被 AEDT 拒绝
  （`GrpcApiError`）后，同一个 worker 进程内**后续所有调用**都报 GetSetups 错误或
  “Failed to start new AEDT gRPC session on port 0”，只能重启 worker。
- **证据**：`docs/evidence/efficiency_investigation.json`、`docs/decisions/efficiency.md`。
- **现有兜底**：报告类调用默认关闭；失败即整次运行失败；worker 进程按次隔离。
- **想请教**：
  1. PyAEDT/AEDT 侧有没有"隔离一次失败命令"的办法（子进程、独立 `Hfss` 会话、或某种 reset 接口）？
  2. 这个毒化是 PyAEDT 1.x 的已知问题吗？升级版本是否能缓解（当前 PyAEDT 版本随 AEDT 2026 R1）？

## 3. 某些几何组合不收敛（`E_NOT_CONVERGED`）

- **症状**：`ring_outer≈2.2`、`disc_factor≈1.17` 附近，8 次自适应后 `assessment=not_converged`；
  12 次自适应时求解本身要超过 50 分钟（被 guard 上限截断）。
- **我们已知**：`ring_outer < 2.0 mm` 会违反同轴壁半径规则（模型直接拒绝）；不收敛点不在这个违规区。
- **想请教**：
  1. 这类"参数贴着可行区边界"的几何，通常该调 mesh/自适应（MaxDeltaS 0.02→0.05？）、
     还是调端口/求解设置？我们目前只能靠"多给自适应次数"。
  2. 有没有办法**先估计**某个几何的收敛难度（例如预估网格量、或先跑粗网格）？

## 4. 求解"卡死但无信号"

- **症状**：一次运行 guard 状态停在 `SOLVING`、`updated_utc` 不再更新，8 个 `hf3d` 进程 90 分钟只烧了
  120 CPU 秒；三个检测信号全部失明（见下）。
- **我们的检测与失败原因**：guard 状态 `SOLVING` 属正常态且无心跳；整机 CPU 信号在本环境不可靠
  （`psutil.process_iter` 看不到 ansysedt/hf3d）；阶段超时不能用于 SOLVING（会误杀正常长求解，实测误杀过一次）。
- **现有兜底**：**墙钟预算**（默认 2700 s/次）到点杀进程并重试一次。
- **想请教**：
  1. 有没有从 AEDT 侧拿到"求解进度心跳"的可靠办法（日志文件 tail、`GetSolverStatus`、进程 I/O 计数器、WMI `Win32_PerfFormattedData`）？
  2. 能否区分"求解慢"与"求解挂死"（例如 `hf3d` 子进程数/内存增长）？

## 5. AEDT 用 `-ng`（无界面）是否真的更稳，未实测

- 现状：软件默认仍带界面启动；已加 `--aedt-ng` 开关（v1.41.1）。
- 没有 A/B 数据。机理上只应减少 GUI 相关干扰；对导出/毒化/许可竞争应无影响。
- **想请教**：AEDT 2026 R1 在 `-ng` 下的已知差异（报告/导出/许可证/并发）？值不值得作为默认？

## 6. 单机吞吐（20–25 分钟/候选）

- 现状：单 AEDT、单队列、无并行；一轮 4 个点约 1.5 小时；优化一个 7 维问题需要几天。
- **想请教**：
  1. 同机多 AEDT 实例（多许可证）是否现实，还是必须多机？
  2. 在不牺牲结果可信度的前提下，有没有公认的加速项（更粗的扫频/更少自适应次数但保留收敛判据、GPU 求解、对称性/端口简化）？
  3. 若用多机，推荐的任务分发方式（共享 campaign 目录 vs 各机独立 campaign 再合并）？

## 7. 推荐器缺少"收敛的物理模型"

- 现状：推荐已能给出**近邻实测失败率**（`antopt/risk.py`）与**耗时回归**（`antopt/cost.py`），
  但不知道某个几何**为什么**不收敛、敏感度如何。
- 现有样本：全部 campaign 中带参数与终态的只有 **9 条**（2 次失败），局部校准不足。
- **想请教**：在这种"每次实验都很贵"的场景，推荐用什么方式积累/迁移收敛信息（实验设计？代理模型？
  以网格量/场强为中间变量？）

## 8. 参数敏感度未知（只知道"点是否合法"）

- 现状：可行区靠对每个参数做一维探测 + 二分精修（`tighten_bounds`），没有真实偏导信息。
- **想请教**：是否值得在少量点上做"参数 ±δ"的敏感度实验？δ 怎么选（制造步长 0.1 mm？）？

## 9. 长跑稳定性缺少系统化故障注入

- 现状：已验证单次停滞、残留 AEDT、进程崩溃后队列续跑；未做组合故障（断网、断电、磁盘满、
  RDP 断连、许可证被抢占）的 3–5 轮注入实验。
- **想请教**：这种"长跑 + 真实硬件"的稳定性验证，业界常做的**最小故障注入集**是什么？

## 10. 辐射效率在本设计上不可得（已定论，供参考）

- 三条路径都失败：直接性报告被拒、全向网格毒化会话、PyAEDT 无 `RadiatedPower/AcceptedPower` 量。
- 详见 `docs/decisions/efficiency.md`。**想请教**：如果拿到同轴壁半径/端口功率的设计导出，是否有其他途径
  不靠 far-field 报告算出 η（如 HFSS field summary powers）？
