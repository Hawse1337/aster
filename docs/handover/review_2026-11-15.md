# 天线仿真系统评审与改进报告

日期：2026-11-15。对象：`<repo>`（检查时 HEAD `1581dfd`，软件版本 1.42.0）及只读检查的 `<guard-repo>`。环境通过已连接的 Ansys 插件确认：AEDT 2026.1、PyAEDT 1.9.0。

本轮完成了代码审查、四类定向修复、15 项新增回归测试和全部 728 项离线测试。没有启动真实电磁求解，没有修改守护仓，没有发布新版安装包。下面严格区分已验证的代码行为与仍待真机验证的工程假设。

## 1. 先处理什么

**先完善失败后的恢复和结果身份校验，再扩展并行与优化算法。** 当前昂贵求解的一部分损耗来自执行链路；算法也可能把导出故障当成几何风险学习。

| 优先级 | 发现 | 当前处理 |
|---|---|---|
| P0 | 重试仍复用被阻塞的线程池及旧执行器；两次预算不等于两次求解 | 已离线复现，见第 3 节，需改造恢复生命周期 |
| P0 | 频率单位未换算；带宽可跨过不达标频点 | 本轮修复 |
| P0 | CPU 监测不可用被当作 0 活动；连接异常被忽略 | 本轮修复 |
| P0 | 导出完整性、解的身份与会话故障没有充分解耦 | 守护层改造方案见第 4 节 |
| P1 | “本设计没有效率量”的证据不能证明枚举完整 | 发现 PyAEDT 默认枚举陷阱，建议重新进行只读探测 |
| P1 | 几何风险混入环境故障；样本仅 9 条 | 先修标签与采样设计 |
| P2 | 多实例、GPU、无界面默认值 | 先建立隔离与配对基准，暂不直接切换 |

## 2. 已写入项目的修复

### 2.1 S11 解析与带宽

`aster/touchstone.py` 原先承诺返回 GHz，却直接使用文件第一列；Hz/MHz 文件会显示错误横坐标。现按选项行统一换算 GHz，支持大小写、内联注释及默认选项，忽略非有限数值行，避免 NaN/Inf 被计为有效采样。

原带宽函数先删除不满足阈值的点，再拼接剩余点。例如 24、24.5、25、25.5、26 GHz 的 S11 为 −12、−12、−4、−12、−12 dB，原实现会给出 2 GHz；正确的最大连续已测通带只有 0.5 GHz。现按频率顺序遇不达标点断开；重复频率取最不利值，非有限值断开。新增 `max_gap_ghz` 供不同网格显式设置，默认 1.5 GHz 保留旧策略。

**影响边界：** S11 解析用于界面曲线；该带宽辅助函数目前未接入 guard 的生产指标计算，因此不能把这次修复说成“历史优化指标全部已纠正”。仅凭剩余点也不能推断缺失频点，生产准入仍需按请求网格核验。

### 2.2 监测失效不再触发假停滞

`aster/stall.py`：缺少 psutil 或 CPU 读取失败时返回未知；采样异常、NaN/Inf、负数会清除观察窗口而不触发停滞。累计计数器回退时重新建立基线，避免负差值被解释为卡死。有效的低 CPU 窗口仍保持原行为。

这解决的是**未知信号误杀**，没有解决整机 CPU 无法归因的问题：其他程序繁忙仍会掩盖求解器停滞，低 CPU 也不证明死锁。

### 2.3 连接失败立即停止

`aster/gui/runner.py`：原来 `connect()` 异常会被吞掉，随后仍进入建模。现统一处理异常以及显式 `False` / `connected=False`，以 `AEDT_CONNECT_FAILED` 终止本次任务并持久化中文失败信息。正常连接与不提供 connect 方法的测试桥仍兼容。

### 2.4 失败解释不再超出证据

`aster/failures.py` 不再把导出短文件直接归因于“扫频未解完”，也不再声称三次失败证明几何解不出来；收敛失败不再固定描述成“8 次”；CreateReport、port 0、STALLED 的说明改为可观测事实与检查动作。未自动放宽收敛阈值。

验证：新增 `tests/test_handover_regressions.py` 共 15 项；修复前复现失败，修复后连同相关旧测试共 59 项通过。项目完整测试 **728 项通过**，比交接文档的 713 项增加 15 项。源码改动未提交、未打新 tag、未重建分发包。

## 3. 必须优先改造的恢复缺陷

`RealRunManager._evaluate_with_stall_watch` 使用单线程 `ThreadPoolExecutor`。`future.cancel()` 不能取消已经运行的函数；旧调用阻塞时，第二个 `evaluate` 排在同一线程后，墙钟却已经开始计时。重试也没有重新走 `ensure_aedt → PID → bridge → prepare`。

本轮离线故障注入：设置两次尝试、每次 0.03 s，第一调用由 Event 阻塞。结果 `actual_evaluate_calls=1`，返回却声称 `stalled 2 time(s)`。证据：`docs/evidence/handover_retry_probe.json`（明确为模拟，不是 HFSS 实测）。现有重试测试的假执行器 0.3 s 后自动返回，无法覆盖无限阻塞。

建议下一次实现按下列生命周期做完整改造，不能只新开一个线程池：

1. 每次尝试拥有独立 attempt_id、worker 进程、显式 AEDT PID/端口及项目副本。
2. 超时后先取消该 run 的 guard 等待/提交权限，再终止本次拥有的进程，等待退出确认；确认失败进入 `RECOVERY_REQUIRED`，不启动下一次。
3. 隔离旧尝试的结果回调与写入权（例如数据库条件更新校验 attempt_id）；晚到的成功结果不能覆盖新尝试。
4. 清空旧桥与执行器，重新启动/连接 AEDT，重新准备项目，才开始新的尝试预算。
5. 分开记录 solve、export、recovery 预算，保留最后一次触发原因；达到墙钟预算只证明超时，不证明死锁。

当前 `kill_solvers()` 按进程名终止所有 AEDT/HF3D，且进程枚举失败时可能什么也没杀；它与多实例部署不兼容。必须先改成有所有权的进程清理，记录 PID 和创建时间，防止 PID 复用误判。

## 4. 扫频导出不完整：判据与重试边界

### 可靠信号

官方 `analyze(blocking=True)` 等待分析完成，返回成功/失败；它不能替代特定结果的完整性验证。`are_there_simulations_running` 是桌面活动信号。安装版 `SweepHFSS.is_solved` 的实现实际检查 `get_solution_data()` 是否有返回，**有数据不等于所有请求频点均已完成**，更不证明数据属于本次改参。[分析 API](https://aedt.docs.pyansys.com/version/stable/API/_autosummary/ansys.aedt.core.hfss.Hfss.analyze.html)、[桌面活动 API](https://aedt.docs.pyansys.com/version/stable/API/_autosummary/ansys.aedt.core.desktop.Desktop.are_there_simulations_running.html)

建议准入条件为：本次提交身份匹配 + 求解成功证据 + 自适应收敛证据 + 指定 sweep 的频率覆盖 + 有效复数 S 参数。不要只依赖 GetSetupStatus 或文件行数。

对当前 24–30 GHz、1 GHz 离散扫频，显式请求网格为 24、25、26、27、28、29、30 GHz。先统一单位，再核验唯一频率集合、端点、有限数值、端口数和参数 variation。7 行重复或错频数据也可能“行数合格”。对于 interpolating sweep，要区分求解基频与导出采样网格。

### 只重导出是否可行

可以设计成先重导出；当前 guard 已有部分支持：`CampaignRunner` 有短文件重试，lens28 配置为 **40 次 × 间隔 15 s**，以及 `resume_guarded_run` 路径。但它不等于任意 FAILED 都可恢复：`CampaignRunner.resume()` 遇到终态直接返回；必须核查上层恢复入口对终态和已有证据的处理，不能简单改状态绕过校验。

建议把“已求解但导出失败”独立保存为可恢复检查点。保持项目、解目录及参数不变；在新后处理 worker 中绑定同一 PID/项目/design/setup/sweep/variation，导出到新的临时文件，验证通过后原子替换。限定重导出次数和预算；检测到完整解缺失才考虑重求解。文件时间戳不能单独证明解是新的。

官方支持 sweep 完成后自动导出 Touchstone，可作为独立对照路径，与手动导出的频率集合和 S 参数比较；它也需要校验，不应直接当完成凭据。[自动导出 API](https://aedt.docs.pyansys.com/version/stable/API/_autosummary/ansys.aedt.core.hfss.Hfss.export_touchstone_on_completion.html)

现有 `_finish()` 先导远场，再导 Touchstone，这是此前上下文冲突的规避措施。如果远场报告失败使会话失效，仍可能影响 S11。建议把必需的 S 参数导出与探索性报告放到独立后处理进程，并显式重绑定上下文；不能在没有真机对照的情况下简单交换两步顺序。

## 5. 会话失效：隔离对象与隔离进程不同

同一个 Python 进程中新建 `Hfss` 对象，不保证获得独立的底层桌面/gRPC 状态。失败后 `disconnect` 可以尝试释放句柄，但不能作为已修复证明。现有 guard `_export_with_retry` 在重试回调失败时继续执行，也应记录重连是否成功。

建议将不稳定报告操作置于独立、可销毁的后处理进程；一次失效即废弃该进程，再由 supervisor 用显式 PID/端口重连。先尝试保留已求解的 AEDT；若独立进程也无法健康连接，再进入 AEDT 重启恢复。不要在活跃求解中反复通过同一 gRPC 通道探测，它可能与分析调用一起阻塞。

`release_desktop` 的关闭参数需显式传递，避免退出后处理 worker 时关掉生产桌面；不能假定新对象或上下文管理器的默认生命周期适合长驻服务。[会话生命周期](https://aedt.docs.pyansys.com/version/dev/User_guide/desktop_sessions.html)

没有查到足以将该症状认定为“PyAEDT 1.9.0 已知且升级必修复”的证据。升级应固定环境，在同一只读/复制工程上复现“有效报告→故意无效报告→有效报告”，比较旧进程、全新进程与重启 AEDT 三种恢复边界，再选版本。

## 6. 卡死检测：心跳、进度、预算分开

心跳只证明监督程序活着；日志更新或 CPU 增长也不等同于数值收敛。建议分别持久化：

| 字段 | 含义 | 用法 |
|---|---|---|
| supervisor heartbeat | 监控/调度进程仍能更新 | 发现监控失联 |
| solver progress | 当前 pass/phase、网格数、求解日志事件及偏移 | 判断是否有实际活动证据 |
| resource sample | 本次进程树 CPU 累计量、I/O、内存 | 辅助诊断，不独立证明卡死 |
| wall budget | 每次尝试及总任务的时间上限 | 最后兜底，记为超时 |

先利用已知 PID 直接查询进程，不依赖整机枚举。权限不足时写 `unknown`；WMI/性能计数器也需要本机验证权限及 PID 对应关系，不保证比 psutil 更可靠。读取独立求解日志/profile 的进度须以实际日志格式为准；只记录文件长度变化也可能被重复错误刷屏误导。

慢与挂无法靠一个通用阈值绝对区分。多信号无进展时标记“疑似停滞”，保留诊断，再由预算结束本次运行。SOLVING 的状态更新时间不应直接用来误杀正常长求解。此部分需要 guard 的独立监督进程，不能只靠设计侧的阻塞 RPC 轮询。

## 7. 收敛、敏感度与昂贵实验

**问题 3：** 8 次不收敛、12 次超时，可能是迭代预算、局部网格、端口、几何细节或求解频率设置共同作用。应保留每 pass 的 Delta S、四面体数、耗时、内存和端口检查；对窄缝、薄壁、尖角、相切/重叠区域做几何特征记录，再做局部网格或端口设置的单因素对照。

MaxDeltaS 从 0.02 放宽为 0.05 是改变质量门槛，不能据此宣布原问题已解决。粗网格可用于预筛，但须标记为低保真；最终候选回到统一验收标准。宽频指标还需要检查自适应频率覆盖，单频收敛不自动证明整段频带精度。[HFSS 自适应方法](https://ansyshelp.ansys.com/public/views/secured/electronics/v261/en/Subsystems/HFSS/Content/HFSS/AdaptiveMeshingMethodsInHFSS.htm)

**问题 7：** `risk.measured_outcomes` 当前把所有 FAILED 都编码为失败，尚未区分几何/收敛失败与许可证、会话、导出、磁盘故障。它可以叫“运行失败率”，不能直接叫“几何不收敛概率”。建议分别学习 `p(convergence_failure | geometry, solver settings)` 与环境失败率；预算超时是删失信息，不应直接赋值为物理不收敛。先清标签，再增加模型复杂度。

9 条样本不足以校准 7 维局部风险。下一轮优先选基准重复点、失败点的邻近对照及当前最敏感的 1–2 维；成功、失败、重导出成功都记录 attempt_id 与设置。网格量/场强可以作中间特征，但真实求解后才知道的量不能在推荐时作为已知输入，除非有明确的廉价预估步骤。

**问题 8：** 值得做有限差分，但不要统一取 0.1 mm：`disc_factor` 是无量纲参数。每个参数按尺度、制造精度、几何合法区间和仿真重复误差选择 δ。在可行区内部取中心差分，边界取单边差分；先重复基准估计噪声，再对 1–2 个关键参数做 ±δ，必要时对照 δ/2。比较归一化灵敏度，记录差分点的网格/收敛标准，避免将数值噪声当成物理敏感度。

## 8. 吞吐与无界面

**问题 5：** `-ng` 是可测的部署选项，不是稳定性保证。GUI/无界面用相同工程副本、参数、核数和软件版本，随机或交替执行配对测试，记录求解/导出耗时、内存、导出完整性和错误。4 次只能做冒烟，不能证明历史约 30% 的间歇失败已消除。当前 `setup_config_code` 及桥接里仍有 `non_graphical=False`；在显式附着既有 PID/端口时的实际行为需检查，启动开关存在不代表全链路一致。

**问题 6：** 同机多 AEDT 从会话机制上可行，是否有足够的并发求解授权必须以实际许可证 entitlement 与 checkout 为准。HPC 核数许可不应简单等同于第二个并发任务许可。[Desktop 会话 API](https://aedt.docs.pyansys.com/version/stable/API/_autosummary/ansys.aedt.core.desktop.Desktop.html)、[2026 R1 许可指南](https://ansyshelp.ansys.com/public/Views/Secured/corp/v261/en/pdf/Ansys_Inc._Licensing_Guide.pdf)

当前软件会拒绝多个无法区分的 AEDT，进程清理又按全局名称执行，所以“多开两个 worker”不能安全实现并发。先做到每槽独立 PID/端口、worker、项目副本、临时目录、锁及资源配额，再比较单槽与双槽的完成数/小时和失败率。内存/磁盘争用可能抵消吞吐收益。

多机采用中心调度及任务租约、每机本地 SQLite 和本地项目，完成后按运行 ID/参数/配置哈希合并结果。不要让多机并发写同一网络共享 SQLite，也不要并发修改同一 `.aedt`。这是建议架构，不是当前已实现能力。

加速优先级：先减少无谓重求解；再做单候选核数基准；然后比较 interpolating 与 discrete sweep，并以关键频点离散验证带宽边缘和窄谐振。官方说明插值扫频可少解频点，但最终精度仍须验证。[插值扫频说明](https://ansyshelp.ansys.com/public/views/secured/electronics/v261/en/Subsystems/HFSS/Content/HFSS/InterpolatingFrequencySweepsinHFSS.htm)

对称性简化仅在几何、激励、材料和所需场分布满足对应对称条件时采用。GPU 是否有收益取决于求解器路径、矩阵规模、硬件及许可，不能仅增加 `gpus=1` 就许诺提速。[GPU 支持说明](https://ansyshelp.ansys.com/public/Views/Secured/Electronics/v261/en/Subsystems/HFSS3DLayout/Content/HFSS/GPUAcceleration.htm)

## 9. 最小故障注入集

以下是针对此系统建议的最小集合，不声称是行业统一标准。先在假适配器/临时数据库中覆盖组合，再对已授权的独立实验 campaign 做少量真机复验。

| 场景 | 故障位置 | 验收条件 |
|---|---|---|
| worker 异常退出 | claim 后、submit 后、结果提交前 | 不丢任务、不重复计入实测；提交身份可追溯 |
| RPC 永久阻塞 + 终止失败 | SOLVING | supervisor 仍可响应；旧尝试未结束时不并发重试 |
| 短文件/重复频率/错单位 + 导出报错 | EXPORTING | 不写假带宽；可从已验证解恢复导出 |
| 磁盘写入异常/SQLite 锁竞争 | 事件、artifact、最终入库 | 部分文件不可见为成功；已保存证据不被覆盖 |
| 许可证拒绝/服务断连 | 求解前、运行中 | 区分环境故障与物理失败；有限退避 |
| 主机重启或 RDP 断连 | 活跃任务 | 从持久记录核实原进程与结果，不盲目重复提交 |

不需要为首轮验证真正断电或填满生产磁盘：模拟 I/O 失败即可覆盖应用层纪律，实际重启/会话断开另做受控验收。每场景记录输入、预期不变量、实际事件和恢复后的任务数；组合故障重点测“导出失败 + worker 退出”和“超时 + 终止未确认”。

## 10. 辐射效率：应重开证据检查

本机 PyAEDT 1.9.0 的 `visualization/post/common.py` 中，`available_report_quantities()` 在没有 `quantities_category` 时循环类别，遇到**首个非空列表即返回**。现有 `quantities_probe.json` 只存 Far Fields、Fields、S-parameters 的平面列表，没有各数量类别、solution 或 context 的完整记录。因此它不能证明“设计仅有 Gain、没有 Directivity 或功率”。原始探测的调用参数未保存在该 JSON 中，此处不能断言原脚本一定漏传了参数，但证据确实不足。

建议把状态从“已定论不可得”降为“当前集成未获得、证据待补”，仍保持 UI 不提供该指标。检查步骤：

1. 在独立只读后处理 worker 中，指定正确 project/design 和已保存远场的 setup/sweep；S 参数 sweep 设置了 `save_fields=False`，不要自动假定它包含所需的所有远场。
2. 指定实际 Infinite Sphere，枚举 report type、可用 solutions 和 **每个 quantities category**，分别保存结果；可参考安装版 `get_all_report_quantities` 的逐类别实现，但仍须明确 context。
3. 特别检查 Far Fields 的方向性类别和 Antenna Parameters，避免只在 Fields 类别中查功率。官方存在独立的 AntennaParameters 报告接口。[可用量枚举](https://aedt.docs.pyansys.com/version/stable/API/visualization/_autosummary/ansys.aedt.core.visualization.post.post_common_3d.PostProcessor3D.available_report_quantities.html)、[AntennaParameters](https://aedt.docs.pyansys.com/version/stable/API/visualization/_autosummary/ansys.aedt.core.visualization.report.field.AntennaParameters.html)
4. 只对确实可枚举的量取数，不盲试 CreateReport；失败即废弃探测进程。一次枚举失败只证明该上下文未成功，不能证明物理量不存在。

效率定义为辐射功率/接受功率。若由 Gain/Directivity 推导，必须保持频率、方向、激励归一化及增益定义一致，特别区分 Gain 与 RealizedGain；仅有一个同轴半径和端口功率不足以推出辐射损耗。全场功率积分也必须核对积分面与损耗项。官方可计算天线参数的前提包括 radiation/PML 边界。[辐射效率定义](https://ansyshelp.ansys.com/public/Views/Secured/Electronics/v251/en/Subsystems/HFSS/Content/HFSS/RadiationEfficiency.htm)、[天线参数计算](https://ansyshelp.ansys.com/public/Views/Secured/Electronics/v261/en/Subsystems/HFSS/Content/ReportsandPostProc/ComputingAntennaParameters.htm)

本轮没有重新导出效率数据，不能宣称效率已经可用。
