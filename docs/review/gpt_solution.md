HFSS 天线智能优化系统可靠性改造任务书
一、项目背景与总体目标
我目前正在开发一套基于 AI Agent、MCP 和 Ansys HFSS 的天线自动设计与优化系统。
主要研究对象为：
3D 打印全金属周期结构漏波天线（Periodic Leaky-Wave Antenna）。
金属透镜天线（Lens Antenna）。
现有系统能够通过 MCP 与 HFSS 交互，执行建模、修改参数、运行仿真、读取结果等操作，同时正在尝试集成遗传算法。
但在多轮次自动优化中，发现以下问题：
Agent 在长时间执行任务后可能遗忘原始设计目标，例如只关注 S11 的改善，忽略增益或方向图。
Agent 可能在 HFSS 仿真完成、读取结果后，未保存工程或导出数据便结束任务。
Agent 缺乏明确的任务状态管理，无法可靠判断哪些任务已完成、哪些任务需要继续。
某次参数调整可能改善一个指标，却破坏其他已经满足要求的指标。
仿真结果和设计决策没有形成可靠的可追溯记录。
本次任务的目标不是开发新的天线优化算法，而是优先建立系统的可靠性基础。
核心原则：由 AI Agent 负责设计决策，由确定性的 Python 程序负责约束检查、流程控制、数据保存、状态管理和结果评价。
需要开发以下三个模块：
DesignSpecManager：设计规范与约束管理模块
SimulationGuard：HFSS 仿真执行保护与恢复模块
AntennaEvaluator：多指标自动评价与最优设计保护模块
三个模块必须能够集成到现有 MCP–HFSS 工作流中。
二、开发前必须完成的工作
在编写代码之前，请先检查现有项目。
重点确认：
当前 MCP Server 的代码结构、工具接口和调用逻辑。
HFSS 是通过 PyAEDT、AEDT Scripting 还是其他方式控制。
HFSS 进程的创建、连接、退出及异常处理机制。
当前天线模型的参数化方式和工程保存位置。
仿真结果目前通过什么方式读取、保存和传递。
已有的遗传算法或优化逻辑如何调用仿真。
当前是否已有任务数据库、日志系统或 checkpoint 机制。
请以实际代码和接口为准，不要假设不存在的功能已经实现，也不要擅自使用未经验证的 PyAEDT API。
完成检查后，先给出简短的现有架构分析，再提出最小侵入式的修改方案。
优先使用 Python、SQLite 和 JSON 等轻量化技术。除非有充分理由，否则不要引入新的大型 Agent 框架。
要求保留现有功能，避免破坏已经正常工作的 MCP 工具。
模块一：DesignSpecManager
1.1 目标
建立一个独立于 LLM 对话历史的设计规范管理系统。
即使 Agent 的上下文被压缩、重置或遗忘，设计要求也必须能够被准确恢复。
系统不能依赖 Agent 自己记住之前的所有指令。
1.2 功能要求
功能 A：创建并保存设计规范
为每个天线项目维护一个 design_spec.json 文件。
至少包含：
基础信息
项目名称、设计类型、规范版本。
工作频率范围及单位。
设计变量及其上下限。
设计变量的单位及物理含义。
制造方式及制造约束。
电磁性能要求
S11 或其他匹配指标。
实现增益（Realized Gain）。
主波束指向。
副瓣电平（SLL）。
工作带宽。
其他可扩展指标，如效率、极化、交叉极化等。
约束分类
Hard Constraints：必须满足的硬约束。
Soft Objectives：希望尽量改善的优化目标。
Protected Metrics：已满足要求、后续修改中需要重点保护的指标。
每项指标应支持：
指标名称及单位。
比较运算符和目标值。
适用频率范围或频率采样点。
必要时的角度范围、极化及其他评价条件。
是否启用。
是否为硬约束。
不要将示例数值写死在程序中。
功能 B：规范不可被无意修改
设计规范应该作为唯一权威数据源。
Agent 可以读取设计规范，但不能通过普通参数优化调用，擅自修改原始设计目标。
如需修改设计目标，应使用独立的更新接口，并满足：
明确指出需要改变的指标。
记录修改原因。
创建新的规范版本。
在日志中记录修改前后的差异。
重大目标修改需要用户明确批准。
所有仿真记录都必须关联对应的规范版本。
功能 C：每轮任务自动加载规范
每轮优化开始前，自动加载当前设计规范，生成结构化的任务状态摘要。
摘要至少包含：
当前设计目标及硬约束。
当前已完成的迭代次数。
当前最佳可行方案。
当前尚未达标的指标。
当前求解任务的状态。
推荐的下一步优化目标。
该摘要可以提供给 LLM 使用，但所有强制性规则必须由程序独立检查，不能仅依赖提示词。
1.3 建议接口
实现类似以下接口，允许根据现有项目适当调整名称：
create_spec()
load_spec()
validate_spec()
update_spec_with_approval()
get_active_constraints()
get_task_context()
get_spec_version()
1.4 验收标准
必须通过以下测试：
重启 Agent 后仍能完整恢复设计目标。
长时间多轮优化不会导致硬约束丢失。
Agent 不能通过普通优化接口修改设计目标。
修改设计规范后，旧仿真结果仍能追溯到原来的规范版本。
设计规范缺少必要字段或单位错误时，系统应拒绝启动相关优化任务并给出明确错误信息。
模块二：SimulationGuard
2.1 目标
构建一个具有状态管理、自动保存、异常恢复和重复执行保护能力的 HFSS 仿真管理器。
本模块的最高优先级是避免昂贵的全波仿真结果丢失。
仿真流程不能依赖 AI Agent 主动记得保存。
2.2 仿真状态机
为每次仿真建立独立的 run_id。
至少定义以下状态：
CREATED：任务已创建。
PREPARED：几何模型与求解设置已准备。
SOLVING：HFSS 正在求解。
SOLVED：求解已经完成。
EXPORTING：正在保存和导出结果。
VALIDATING：正在校验结果完整性。
COMPLETED：结果已完整保存并通过验证。
RECOVERY_REQUIRED：存在可恢复的异常或未完成操作。
FAILED：发生无法自动恢复的错误。
需要明确规定合法的状态转换，并通过程序强制执行。
只有在完成数据保存和完整性验证后，任务才能进入 COMPLETED。
2.3 自动保存功能
要求系统在以下阶段进行必要的保存：
开始求解前保存 HFSS 工程。
求解完成后保存工程以及可恢复的求解数据。
将所有必需的结果导出到独立文件。
验证文件及数据完整性。
将成功状态写入任务数据库。
每次仿真至少需要保留：
完整的输入参数。
对应的设计规范版本。
HFSS 工程文件及有效的求解数据。
求解配置、软件版本等必要元信息。
S 参数数据。
按设计规范要求的方向图数据。
增益等性能评价数据。
求解日志和异常记录。
最终任务状态。
需要特别注意，保存 HFSS 工程文件并不必然意味着求解数据、远场数据都已经可以独立恢复。请根据实际 HFSS/PyAEDT 版本验证保存行为。
2.4 数据完整性检查
不能仅仅通过“文件存在”判断保存成功。
校验程序应检查：
输出文件是否可正常读取。
数据是否为空。
频率单位是否正确。
频率采样是否覆盖设计要求。
必要的远场角度、极化和频点是否齐全。
是否存在 NaN、Inf 或明显不合法的数据。
求解数据是否对应当前模型和求解配置。
是否存在未完成或失败的求解状态。
缺失必要数据时，不能标记为 COMPLETED。
2.5 异常恢复
必须考虑以下情形：
情形一：HFSS 已完成求解，但 Agent 中途退出。
重新启动后，应优先检查原工程、HFSS 进程及求解数据，尝试恢复保存或导出操作，而不是直接重新求解。
情形二：导出结果时发生异常。
如果已经存在有效求解数据，应允许仅重试结果导出。
情形三：Agent 发出结束任务指令，但仿真尚未提交。
系统应阻止该任务进入完成状态，并尝试执行清理、保存或恢复流程。
情形四：HFSS 崩溃或系统意外退出。
启动后应根据持久化的状态记录检查已有文件，恢复可恢复任务，并对不可恢复任务进行明确标记。
情形五：重复提交同一仿真。
如果几何参数、结构类型、设计规范、求解配置等一致，且已有有效结果，应优先复用缓存，避免重复计算。
缓存标识应包含足以判断结果是否可复用的完整输入信息，不能仅依赖几何参数或文件名。
2.6 数据库及原子性要求
建议使用 SQLite 保存仿真任务和状态记录。
需要支持：
按 run_id 查询任务。
按设计参数和求解配置查询已有结果。
记录执行时间及失败原因。
更新状态并验证状态转换是否合法。
避免并发任务错误覆盖同一工程。
避免多个进程重复提交同一个仿真任务。
输出文件建议采用临时文件写入、校验完成后再提交的方式。
数据库状态更新与文件持久化之间需要设计明确的恢复规则，避免程序崩溃时产生“数据库显示完成，但文件不完整”的情况。
对于无法确认状态的任务，应保守处理并保留已有数据，不要自动删除或覆盖。
2.7 建议接口
create_run()
prepare_simulation()
execute_simulation()
save_project_and_solution()
export_required_results()
verify_artifacts()
recover_interrupted_run()
find_reusable_result()
get_run_status()
建议对 MCP 暴露统一的安全调用入口，例如 run_guarded_simulation()。
不要允许普通优化流程绕过该入口，直接运行不受保护的 HFSS 求解。
2.8 验收标准
必须通过以下测试：
正常仿真可以完整保存数据并进入 COMPLETED。
求解完成后人为终止 Agent，重新启动后能够发现未完成的保存任务。
若有效求解数据仍然存在，系统应尝试恢复导出，不应无条件重新求解。
导出文件故意缺失时，不能将任务标记为完成。
重复提交已完成的相同任务时，应复用有效结果。
模拟 HFSS 求解失败后，系统能正确记录失败原因。
多轮连续运行时，不会因为文件路径冲突而覆盖先前的有效仿真结果。
对所有恢复场景，应区分模拟测试和真实 HFSS 集成测试。不能仅凭 Mock 测试成功，就宣称实际求解恢复已经验证。
模块三：AntennaEvaluator
3.1 目标
实现独立于 LLM 的天线性能自动评价系统，避免 Agent 在优化某个指标时忽略其他指标。
评价应基于 HFSS 导出的真实数值结果，而不是依赖 LLM 对曲线截图的主观判断。
3.2 指标提取
首先支持以下指标：
S 参数
根据指定端口、参考阻抗及频率范围读取 S11。
支持：
最差频点 S11。
满足匹配要求的频率区间。
阻抗匹配带宽。
增益
根据实际导出数据计算或提取：
指定方向的实现增益。
主波束峰值实现增益。
工作频带内的最小实现增益。
必须区分 Gain、Realized Gain 和 Directivity，不能混用。
主波束方向
从远场数据中计算：
指定角度切面下的主波束指向。
与目标角度的偏差。
主波束方向随频率的变化。
漏波天线应允许目标波束方向随频率变化。
副瓣电平
根据规定的方向图切面、搜索角域和主瓣排除规则计算 SLL。
不能简单地将方向图的第二大采样值当作副瓣峰值。
综合有效带宽
定义同时满足所有已启用硬约束的工作频率集合。
在此基础上，识别满足要求的连续工作区间，计算综合有效带宽。
需要明确频率采样分辨率；不得将两个采样点之间未经验证的区域自动判定为合格。
3.3 多目标约束判定
针对每个候选方案生成完整的指标报告。
每个指标至少包括：
实际测量或计算值。
对应目标值。
是否达标。
违反约束的程度。
数据质量或完整性状态。
最终将候选方案分为：
FEASIBLE：全部硬约束满足。
INFEASIBLE：至少一项硬约束未满足。
INVALID：数据不完整、数值无效或无法可靠评价。
不能把 INVALID 当作一个普通的低分设计继续参与优化。
对于 INFEASIBLE 方案，应保留完整的违反约束信息，以便后续优化器使用。
3.4 保护最佳可行方案
系统必须维护一个独立的 Best Feasible Design Archive。
规则如下：
不允许未验证的新方案覆盖已验证的最佳可行方案。
不允许因为单一指标改善而忽略其他硬约束。
不可行方案可以保存，但应与可行方案明确区分。
不同优化目标下的可行方案可以共同保存在 Pareto 解集中。
任何设计被选为当前推荐方案时，必须说明依据及对应规范版本。
最佳方案不是简单地选择某个综合分数最高的个体。
如果存在多个非支配可行方案，应保留它们，并使用明确的决策规则或由用户选择最终方案。
3.5 历史数据库
每次仿真完成后，保存：
结构类型与完整几何参数。
仿真任务编号。
指标结果。
可行性状态。
约束违反信息。
Pareto 支配关系或对应解集版本。
与先前方案的性能差异。
Agent 对修改的设计理由（如果存在）。
数据应可以导出为 CSV 或其他常见格式，供后续遗传算法、代理模型和统计分析使用。
3.6 与现有优化算法的集成
请开发统一的评价接口，让遗传算法及后续优化器直接调用。
例如：
evaluate_design()
extract_antenna_metrics()
check_constraints()
calculate_constraint_violation()
update_pareto_archive()
get_best_feasible_design()
compare_designs()
原有遗传算法应尽量复用这些接口，不要重新实现另一套独立的天线指标计算规则。
暂时不要求重新设计遗传算法的搜索策略。
3.7 验收标准
必须完成以下测试：
S11 优化成功但方向图恶化时，系统能正确识别不满足硬约束。
在增益合格但副瓣不合格时，结果被标记为 INFEASIBLE。
不完整的方向图数据不能被错误判定为合格。
全频段综合有效带宽计算符合明确的采样和连续区间定义。
已保存的最佳可行方案不会被更差或不可行的方案覆盖。
相同的 HFSS 数据输入多次，应得到一致的指标结果。
当存在多个 Pareto 非支配可行方案时，能够正确保存和查询。
四、三个模块的集成要求
三个模块应组成以下工作流程：
Agent 读取设计规范与当前状态。
Agent 或优化算法提出新的候选结构和参数。
DesignSpecManager 检查任务约束及设计规范版本。
SimulationGuard 创建独立的仿真任务。
HFSS 执行建模和求解。
SimulationGuard 保存、导出、校验和提交结果。
AntennaEvaluator 自动计算所有指标。
系统更新可行性状态、历史数据库及 Pareto 解集。
Agent 获取结构化结果摘要，决定下一步优化。
重复执行，直至达到停止条件或仿真预算上限。
特别要求：Agent 不得通过直接读取 HFSS 的部分结果来绕过保存和评价流程。
系统应确保原始数据先被可靠持久化，随后才交给 Agent 进行设计判断。
如果历史遗留 MCP 工具允许绕过保护层，请明确列出这些接口，并设计兼容或限制机制。

六、实施顺序
请严格采用分阶段开发。
第一阶段：现有系统分析
阅读关键代码及现有 MCP 工具定义。
绘制实际调用关系。
找出仿真结果可能丢失的节点。
给出模块改造计划。
明确与现有代码的兼容方式。
第二阶段：设计规范管理
实现 DesignSpecManager。
完成规范验证、版本管理和只读约束机制。
编写单元测试。
第三阶段：仿真可靠性保护
实现 SimulationGuard。
加入状态机、自动保存、结果校验和恢复。
与真实 HFSS 控制接口集成。
进行异常注入测试。
这是优先级最高的阶段，不能因为开发新功能而省略可靠性验证。
第四阶段：天线自动评价
实现 AntennaEvaluator。
完成指标提取、约束判定和最佳方案保护。
接入现有优化流程。
第五阶段：端到端验证
使用已有的参数化天线工程完成测试。
至少验证：
一次完整仿真能够可靠执行并保存。
连续多轮修改不会遗忘设计约束。
改善 S11 但破坏方向图时能够识别。
求解完成后中断 Agent，可以检查并恢复任务。
重复请求不会无条件重新运行 HFSS。
可以恢复历史记录和最优可行方案。
不要使用实际生产项目进行破坏性测试。优先使用独立工程副本。
七、开发纪律与额外要求
禁止静默失败。 任何保存失败、校验失败、求解失败都必须产生明确状态及日志。
禁止覆盖有效成果。 所有新的候选设计和仿真结果必须可追溯。未经确认，不得删除原始工程或已有有效结果。
禁止伪造测试结论。 如果由于运行环境限制而无法真正调用 HFSS，必须明确说明哪些测试仅通过 Mock 验证。
禁止编造 API。 PyAEDT 和 HFSS 的方法、参数、返回值必须根据当前安装版本或对应文档确认。
优先保证可靠性，而不是复杂度。 不要为了实现这些功能而引入不必要的多 Agent 协作机制。
保留扩展能力。 未来可能集成 NSGA-II、贝叶斯优化、代理模型以及结构级搜索，所以规范、仿真执行和性能评价接口应尽量保持相互独立。
注意长任务与并发。 MCP 调用超时、Agent 上下文结束，不应被直接等同于 HFSS 求解失败；任务身份和执行状态必须持久化，并考虑资源锁与多进程冲突。
避免无意义重跑。 遇到异常时，优先检查已有工程、有效求解数据和历史缓存。不能在无法确定状态时直接删除原始数据或强制重跑。
保持技术文档同步。 对新增模块、状态转换、异常恢复和 MCP 接口变化提供简明说明。
八、最终交付要求
完成开发后，需要提供：
可以运行的 Python 源代码。
与现有 MCP–HFSS 工作流的集成代码。
三个模块的接口说明。
配置文件示例。
数据存储结构说明。
自动化测试代码。
实际测试结果及未解决问题。
运行、恢复和故障排查说明。
请重点展示以下四类测试结果：
测试 A： Agent 遗忘方向图要求时，系统是否仍能正确评价所有硬约束。
测试 B： HFSS 求解完成后 Agent 中断，系统是否能够恢复和保存已有仿真结果。
测试 C： 同一仿真任务被重复提交时，系统是否能够安全复用已经存在的有效数据。
测试 D： 新设计改善单个指标但破坏其他硬约束时，系统是否能够保护已有最佳可行方案。
在开始实际修改代码之前，请先输出当前架构分析、预期修改文件、实施顺序和可能存在的兼容性风险。
随后按照阶段实施，不要一次性生成大量未经测试的代码。
最终目标不是让 Agent 在提示词中承诺不再犯错，而是从程序架构上保证：即使 Agent 遗忘指令、错误判断或意外退出，也不会轻易丢失仿真结果、忽略设计约束或破坏已有的优秀设计。
